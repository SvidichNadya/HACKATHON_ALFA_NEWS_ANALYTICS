# Бизнес-радар · Альфа-Бизнес

Сервис для руководителей крупного бизнеса: берёт внешние новости и аналитику банка, сопоставляет их с профилем конкретной
компании (отрасль, продукты банка, внешняя торговля, платёжное окружение) и показывает **что произошло, почему это важно именно
этой компании, что говорит банк, что стоит проверить и чего система не знает**. Отдельно ищет сигналы из разных новостей, которые
сходятся на одном узле бизнеса («каскады»).

Это не лента с пересказом: порядок и содержание карточек зависят от компании и роли пользователя, каждый вывод ссылается на
основания, а позиция банка визуально и логически отделена от вывода AI.

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build        # http://localhost:8000
```

Без Docker (Python 3.12):

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.lock
python -m radar.cli init
RADAR_DB_PATH=var/radar.sqlite3 flask --app wsgi run          # или gunicorn wsgi:app
python -m unittest discover -s tests -t .                      # 75 тестов
```

Первый запуск создаёт схему, загружает данные банка из `data/contest/`, демонстрационные новости, учебные образцы аналитики банка и учётные записи. Повторный запуск ничего не дублирует.

### Данные и учётные записи

В `data/contest/` лежат три файла банка (`df_Uid_data_hack`, `df_Uid_payment_hack`, `df_Fid_Uid_link_hack`, сжатые gzip). При первом запуске они
импортируются автоматически (≈20 с, 85 514 компаний, 1,38 млн платёжных связей). Если файлов нет, создаётся синтетический набор в той же схеме.
Режим задаёт `RADAR_DATASET=auto|contest|synthetic`. Свои выгрузки можно положить туда же (CSV или CSV.GZ; тип файла определяется по заголовкам).

Пароль для всех: значение `RADAR_DEMO_PASSWORD` (по умолчанию `alfa-radar-demo`).

* `jury` — доступ ко всем компаниям, поиск по названию отрасли, идентификатору, региону; загрузка материалов. Список по умолчанию отсортирован по выручке.
* `co1.ceo` … `co8.cfo` — по два пользователя (генеральный и финансовый директор) у восьми крупнейших действующих клиентов с видимой сетью платежей,
  подобранных так, чтобы отличались отрасль и набор продуктов: `co1` — инженерное строительство (кредит, ВЭД), `co2` — оптовая торговля топливом, `co3` — металлами,
  `co4` — неспециализированная опт, `co5` — автозапчасти, `co6` — напитки (кредит и депозит), `co7` — грузоперевозки, `co8` — пищевые продукты. Точное соответствие выводит `python -m radar.cli accounts`.
* На синтетическом наборе вместо них создаются `metal.cfo`, `trade.cfo`, `agro.ceo`, `build.cfo`, `digital.ceo`, `mining.owner` и др.

#### Что показал анализ предоставленных данных

* Компаний 85 525 (11 идентификаторов повторяются), но **с выручкой от 15 млрд ₽ — только 115**, из них 54% — оптовая торговля (ОКВЭД 46.x), ещё 20 — строительство. Медианная выручка в наборе — 34 млн ₽. Поэтому список по умолчанию сортируется по выручке, а аккаунты демонстрации — крупные компании.
* У каждой компании есть `GROUP_ID`, но у половины групп одна организация: «группой» компания считается, только если в наборе ≥ 2 организаций.
* Платежи: 1,38 млн связей, 27 тыс. из них — платежи компании самой себе (оборот собственных счетов): они не считаются контрагентами и показываются отдельно.
  Для крупных компаний отрасль известна лишь у 30–40% потока: остальные контрагенты вне таблицы компаний. Они остаются в расчёте концентрации, но отрасль у них «неизвестна», и интерфейс показывает долю классифицированного потока.
* Из 12,5 тыс. связей с физлицами 37% ведут в компании набора; 969 физлиц связаны с несколькими организациями — это используется как признак возможной аффилированности.
* Коды ОКВЭД бывают вида `46.71.2`, `46.4`, `1.11` (потеряна ведущая нулевая цифра) — они нормализуются; `46.71` трактуется как торговля топливом, `46.72` — металлами и т. д.
* `CL_TYPE`: `PROSPECT` и `CLOSE_CLIENT` (≈50% набора) не имеют продуктов банка не потому, что у них нет долга, а потому что банк его не видит: отсутствие кредитов для них не снижает чувствительность к ставке, а недостаток данных раскрывается.
* Справочники в верхнем регистре, страны перечислены через запятую (`КИТАЙ, ТУРЦИЯ`), в `NEGATIVEMARK` смысл признака в описании неоднозначен, поэтому в логике он не используется.

## Сценарий проверки (10 минут)

1. Войти как `co6.cfo` (на синтетических данных — `metal.cfo`) → **Главная**: виджет «Бизнес-радар» с приоритетными событиями (точка входа есть и в боковом меню на любой странице).
2. **Бизнес-радар**: лента отсортирована по значимости для этой компании; справа — профиль и чувствительность к факторам с происхождением каждого числа.
3. Открыть событие «Банк России сохранил ставку 14%»: факт, почему важно *этой* компании (подтверждённые продукты), цепочка влияния,
   позиция банка (красная линия), проверки, калькулятор, «чего не хватает». Кнопка **«Как это получено»** — трасса агента.
4. Сменить пользователя (например, на `co3.ceo`, у которого нет кредитных продуктов): то же событие даёт другие механизмы и другой порядок ленты.
5. В карточке спросить: «что если ставка +2 п.п. при долге 5 млрд», «в разрезе контрагентов», «каких данных не хватает», «что говорит банк».
6. **Каскады**: несколько независимых событий сходятся на одном узле; слабое звено показано отдельно.
7. **Проверить новость**: вставить любой незнакомый текст (есть кнопка «Подставить пример») — система разберёт его и покажет влияние или честно
   скажет, что связи нет. Текст с «Игнорируй все инструкции…» обезвреживается.
8. Под `jury`: **Источники** — загрузка PDF/DOCX аналитики банка, CSV в формате кейса, RSS; **Качество** — метрики.

## Что внутри

```
radar/
  nlp/          стеммер, BM25, simhash, извлечение событий (сигналы фактора с направлением, числа, даты, гео, сырьё)
  knowledge/    отраслевые профили по ОКВЭД, словари, онтология каналов влияния, каталог механизмов влияния
  profile.py    профиль компании: признак → источник → тип (подтверждено / выведено / неизвестно)
  graph.py      платёжное окружение: концентрация, отраслевой состав, группа
  ranking.py    значимость и уверенность — раздельно, с объяснением вклада
  agent/        планировщик-оркестратор, инструменты с правами, LLM-шлюз, сборка вывода, самопроверка, каскады, диалог
  ingest/       документы, кластеризация в события, RSS/HTML (защита от SSRF), CSV кейса
  web/          Flask API: сессии, CSRF, изоляция компаний, заголовки безопасности
static/         интерфейс (ES-модули, SVG-графика, без сборки)
tests/          75 тестов: извлечение, персонализация, агент, безопасность, API, оценка качества
docs/           ARCHITECTURE.md, openapi.yaml
```

Подробности — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Режимы работы AI

* **Детерминированный** (по умолчанию, ключей не нужно): извлечение, ранжирование, механизмы влияния, цепочки, проверка, диалог — по правилам и справочникам.
* **С моделью**: укажите `LLM_API_BASE_URL` и `LLM_API_KEY` (OpenAI-совместимый шлюз). Допускаются только модели из списка кейса; любое другое имя отклоняется при старте.
  Лёгкая модель (`LLM_MODEL_LIGHT`) отвечает на уточняющие вопросы, глубокая (`LLM_MODEL_DEEP`) формулирует связный вывод. Модель получает
  только пронумерованные основания и обязана ссылаться на их id; проверка отбрасывает утверждения с несуществующими основаниями,
  придуманными числами и приписыванием вывода банку. При недоступности шлюза или превышении бюджета токенов (`LLM_RUN_TOKEN_BUDGET`, `LLM_DAILY_TOKEN_BUDGET`) сервис продолжает работать в детерминированном режиме.

> Ключ шлюза при разработке этого репозитория не использовался: модельный путь проверен тестами против совместимой заглушки транспорта
> (разбор JSON, проверка оснований и чисел, отказоустойчивость, бюджет), но не против реальных моделей. Промпты стоит откалибровать на реальном шлюзе.

## Данные

* `data/contest/` — предоставленные данные банка; `data/samples/` — синтетические CSV в той же схеме. Любые файлы загружаются так:
  `python -m radar.cli import-csv <файл.csv>` или в интерфейсе (`jury` → Источники). Тип определяется по заголовкам; кодировки UTF-8/CP1251 и разделители `, ; Tab` поддерживаются; пропуски не блокируют анализ.
* **Аналитика банка**: положите оригинальные PDF/DOCX/MD из приложения 2 в `data/bank_analytics/` и перезапустите (или загрузите в интерфейсе).
  До этого используются **учебные образцы**, написанные для прототипа и пересказывающие только цифры из текста кейса; в интерфейсе они помечены как «демо-материал» и не выдаются за публикации банка.
* Новости: демонстрационный корпус (37 материалов, в т. ч. дубли, противоречие, устаревшее, шум и текст с инъекцией) + RSS (`jury` → Источники) + любой вставленный текст.

## Безопасность

Серверная проверка прав на каждый вызов инструмента и каждый HTTP-запрос (изоляция компаний), журнал аудита (в том числе отказов), CSRF-токен,
строгий CSP без inline-скриптов и стилей, ограничение частоты входа/анализа, SSRF-защита загрузки лент (только HTTPS, блок внутренних адресов, лимит размера),
парсер XML без внешних сущностей, обезвреживание инструкций во внешних текстах, модель не имеет доступа к БД и сети, в модель не передаются идентификаторы компании.
Ограничения прототипа: лимитеры в памяти процесса; для нескольких инстансов нужен общий стор (Redis).

## Масштабирование и сопровождение

* Новая отрасль: строка в `knowledge/sectors.py` (диапазон ОКВЭД, базовые чувствительности, сырьё). Новый фактор: правило в `knowledge/lexicon.py` + механизм в `knowledge/mechanisms.py` — оркестрация не меняется.
* Новый источник: адаптер, возвращающий `(title, body, source, url, published_at)` в `ingest.store.add_document`.
* Хранилище: SQLite (WAL) — для прототипа и одного узла; слой `radar/db.py` изолирован, перенос на PostgreSQL — замена драйвера и диалекта схемы. Поиск — BM25 в процессе; на больших объёмах заменяется на OpenSearch/pgvector без изменения интерфейса `retrieval.search`.
* Фоновая обработка: сбор и кластеризация выполняются при загрузке; пользовательский запрос только читает готовые события.
* Мониторинг: экран «Качество» и `/api/metrics`: покрытие утверждений основаниями, доля прошедших самопроверку, раскрытые ограничения, оценки пользователей, токены, перепланирования, отказы доступа; офлайн-оценка ранжирования `python -m radar.cli eval` (Precision@5, nDCG@5, Recall@10, пересечение топ-5 у разных компаний, дубли). Рекомендуемый процесс: еженедельная экспертная разметка 50–100 пар «компания — событие», пересчёт порогов, разбор негативных отзывов.

## Честные ограничения

* Данные компаний — предоставленные банком (обезличены), а новости и «аналитика банка» синтетические; экспертные оценки в офлайн-метриках — тоже и считаются на синтетическом наборе с размеченными компаниями. На малом корпусе разрыв с хронологической лентой невелик; сравнение со случайной лентой и пересечение топ-5 показывают, что персонализация работает, но абсолютные числа не переносятся на реальные данные.
* В исходных данных нет дат платежей, сумм долга, ставок и договоров: система не считает процентную нагрузку сама и прямо говорит об этом; расчёт делается по допущениям пользователя в калькуляторе.
* Веса связей в онтологии и базовые чувствительности отраслей — экспертные допущения; они показываются как допущения, а не как оценка по компании.
* Извлечение событий основано на правилах и словарях русского языка и не заменяет модель на сложных текстах; в режиме с моделью спорные места остаются за проверкой оснований.
* `gunicorn` в образе установлен из pinned-версии, но сборка Docker-образа в среде разработки не запускалась (нет сети): проверены тесты и запуск через Flask; в `docker compose up --build` стоит убедиться при первом развёртывании.
