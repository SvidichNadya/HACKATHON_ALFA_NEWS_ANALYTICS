# Архитектура

```
 новости (RSS / HTML / текст)        аналитика банка (PDF/DOCX/MD)        CSV кейса
            │                                   │                              │
            ▼                                   ▼                              ▼
   ingest.store.add_document ──► docs/chunks ──► BM25-индекс        companies / payments / persons
            │  извлечение (nlp.extract), защита от инъекций                   │
            ▼                                                                  ▼
   события: кластеризация, противоречия, авторитетность          profile.build_profile + graph.company_graph
            └──────────────────────────────┬───────────────────────────────────┘
                                           ▼
                 knowledge.mechanisms: (сигнал события) × (экспозиция компании) → механизм влияния
                                           ▼
                 ranking.score: значимость (0–100) и уверенность (0–1) раздельно, с вкладом каждого фактора
                                           ▼
        agent.orchestrator: план → инструменты → сборка утверждений → самопроверка → перепланирование → результат + трасса
                                           ▼
             Flask API  ──►  SPA «Бизнес-радар» (лента, карточка, каскады, связи, проверка новости, источники, качество)
```

## Три разделённых вопроса

1. **Связано ли событие с компанией** — `profile` + `graph` + `mechanisms`: механизм создаётся только при наличии основания
   (подтверждённого признака, платёжной связи или отраслевого допущения). Общего запасного шаблона нет: нет экспозиции — нет карточки.
2. **Почему это важно** — тот же объект механизма: `why` (признаки), `how` (канал), `conditions`, `unknowns`, `checks`, `horizon`.
   Значимость и текст берутся из одного объекта, поэтому не расходятся.
3. **Как подать** — `agent.draft` собирает типизированные утверждения; модель (если подключена) только добавляет связный вывод поверх них.

## Контракт данных вывода

Каждое утверждение — объект `claim`:

| Поле | Значение |
|---|---|
| `type` | `FACT` (источник/данные компании), `BANK_ANALYSIS` (дословный фрагмент материала банка), `AI_INFERENCE`, `SCENARIO`, `UNKNOWN` |
| `evidence` | id оснований: `doc:<id>` новость, `bank:<chunk>` аналитика банка, `profile:<признак>`, `graph:recipients|payers` |
| `origin` | `extract`, `computed`, `rules`, `llm` |
| `features` | признаки компании, повлиявшие на вывод |
| `downgraded` | причина, если самопроверка понизила статус |

Инсайт (`insights.payload`): `title`, `priority` (`critical|high|medium|watch`), `confidence` (`high|medium|low`) + `importance`, `confidence_score`,
`what_happened`, `why_you`, `scenarios[]` (риск / возможность / на контроле, условия, неизвестное, горизонт), `chain` (граф), `bank_view`,
`ai_view`, `checks[]`, `calc[]`, `unknown_ids[]`, `sufficiency`, `offers[]` (помечены как реклама), `evidence{}`, `claims[]`, `verification`, `run_id`.
Подробная схема эндпоинтов — `docs/openapi.yaml`.

## Агентная логика

| Требование | Реализация (`agent/orchestrator.py`) |
|---|---|
| Планирование | План выбирается по данным: нет платёжных связей — шаг пропускается и фиксируется как неизвестное; событие из одного источника или с противоречием — добавляется поиск подтверждения |
| Инструменты | `get_company_profile`, `get_event`, `graph_exposure`, `match_mechanisms`, `search_bank_analytics`, `search_news`; каждый вызов проверяет права и пишется в `audit` |
| Контекст | Состояние запуска (`profile`, `event`, `mechs`, `bank`, `related`) переиспользуется на всех шагах; повторный шаг не начинает с нуля |
| Самопроверка | `agent/verify.py`: обязательные основания, существование id, наличие слова банка только при фрагменте банка, числа из оснований, раскрытие противоречий, ограничения при слабых основаниях, шаблоны инъекций |
| Адаптация | Нет аналитики банка → повторный поиск с широким запросом; утверждение модели без основания/с выдуманным числом → отбрасывается; статус правил понижается до «вывод AI»; максимум `AGENT_MAX_REPLANS` |
| Ограничения | `AGENT_MAX_STEPS`, `AGENT_WALL_SECONDS`, `LLM_RUN_TOKEN_BUDGET`, `LLM_DAILY_TOKEN_BUDGET` |
| Трассируемость | Таблица `agent_runs`: план, шаги, аргументы, результаты, время, токены; в UI — «Как это получено» |

Одноагентная схема с набором инструментов выбрана сознательно: шаги зависят друг от друга по данным, а разделение на агентов добавило бы
передачу контекста без выигрыша в качестве.

## Радар каскадных последствий (`agent/cascade.py`)

Онтология (`knowledge/ontology.py`): узлы первого порядка (стоимость долга, закупочные затраты, валютная чувствительность, устойчивость поставок,
давление на спрос, …) → узлы схождения (оборотный капитал, маржа) → исход (ликвидность). Каждый механизм события активирует узлы с силой, равной его влиянию;
сила распространяется по рёбрам (глубина ≤ 3). Каскад создаётся, если на один узел приходят пути минимум от **двух независимых событий** разных факторов.
Уверенность = среднее геометрическое опоры звеньев (доля подтверждённых данных × структурная достоверность рёбер); слабое звено выводится отдельно.
Наблюдаемая концентрация платежей усиливает узел и показана как усилитель, а не как событие. Цепочки не строятся глубже трёх рёбер и при низкой опоре отбрасываются.

## Ранжирование

`importance = 100 · (noisy-OR влияний топ-3 механизмов + бонусы за отрасль/регион/аналитику банка) · свежесть · авторитетность · вес роли`.
Роль меняет порядок, но не факты. `confidence = 0.4·опора экспозиции + 0.4·надёжность факта (источники, авторитетность, противоречия) + 0.2·поддержка аналитикой банка`.
Приоритет: `critical` — значимость ≥ 78, уверенность ≥ 0.6 и подтверждение несколькими источниками или официальным; уверенность < 0.35 понижает до «наблюдение».
Повторяющийся ведущий механизм в ленте штрафуется (×0.82 за повтор), чтобы верх ленты не был пятью версиями одной истории.
Пороги и веса подбираются на экспертной разметке (`radar/evaluation.py`), а не задаются произвольно.

## Безопасность AI-компонентов

Модель не обращается к БД, сети и файлам; оркестратор вызывает инструменты по фиксированному списку, права берутся из серверной сессии.
Внешние тексты проходят `sanitize_untrusted` до извлечения и до попадания в промпт; в системном промпте они объявлены данными.
В промпт не попадает идентификатор компании. Результат модели проходит ту же проверку, что и правила. Журнал аудита хранит инструмент, цель, решение и краткие аргументы без содержимого.
